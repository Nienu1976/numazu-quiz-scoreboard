## 1. 指摘の詳細

### R-01 🔴 Undo の運用契約（events.ts `undo`）
- 現状: `undo(events)` は **末尾の1件を無条件に取り除く**。`apply` が無視したイベント（在席以外への○、done 後の入力、未 done での `finalize` など）がログに残っていると:
  - 無視された○の後に「1手戻す」→ 何も変わらない（運営は「戻らない」と感じて連打し、本当に戻したくない1手まで戻す）。
  - 未 done で押された `finalize` が末尾にある → `undo` は確定扱いで拒否し、**Undo できなくなる**（`unfinalize` でしか外せない）。
- 再現: `review-boundary.test.ts`「R-01」。
- 提案（どちらか）:
  1. エンジンに `dispatch(init, events, ev)` を追加し、**状態が変わったときだけ** ログに積む（`apply(s, ev) !== s` で判定できる）。UI はこれしか使わない。ファズテストはこの運用を前提に一貫性を確認済み。
  2. `undo` を「状態が変わった直近のイベントまで」取り除くようにし、`finalize` の判定もログではなく `replay` 結果の `finalized` で行う。
- 1 の方が単純。どちらにするかは実装者と統括で決める。
- 追記（操作画面 c660ba9 確認後）: `src/control/store.ts` の `r2Dispatch` はすでに 1 の方式で記録している（良い）。`r1Dispatch` は `finalize` だけを確認していて、無視される `setScore`（範囲外・小数・欠席者）は記録されるため、1R では Undo が空振りしうる。全ラウンドの dispatch を 1 に揃えるのが確実なので、エンジンに共通の `dispatch` を置くことを推奨する。

### R-04 🔴 SF タイムアップ（G1 と同じ根）
- 現状: タイムアップはタイマー側（`isTimeUp`）にしかなく、`RoundState` には無い。押し込み分の制限は **イベントに `afterTimeUp: true` が付いているときだけ** 効く。
  - 押し込み分を使ったあとでも、フラグの無い○×は通常どおり受け付ける（再現: 「R-04」）。
  - UI がフラグを付け忘れる、またはタイムアップ後もボタンが押せると、時間切れ後の入力が得点になる。決勝進出を決める場面なので重大とした。
  - 表示画面に「タイムアップ」を出す根拠が状態に無いため、replay（PC 再起動からの復旧）でもタイムアップしたかどうかが分からない。
- 提案: Event に `{ type: 'timeUp' }` を追加する。UI はタイマーが0になった時点で1回だけ積む。`timeUp` 以降は通常の○×を拒否し、押し込み分の1回だけ受け付ける。`timeUp` を Undo 対象にするかは決める必要がある（タイマー操作は Undo 対象外という §1.2 と揃えるなら対象外）。判定確定は `abort` の流用で問題ないが、`lastAction` は「判定確定」にする。

### R-03 🟡 SD で勝ち抜けた人の連答権（round.ts `stepSd`）
- `stepSd` は SD の勝者を `markWin` を通さずに `status='win'` にしているため、連答権がクリアされない。
- 再現: 枠1、A○ → B○（B が連答権）→ 打ち切り → SD → B○ → done 後も `holder='B'`。
- 影響: 表示画面で、勝ち抜け済みの人に連答権の信号灯が点いたまま残る。SD 中に本戦の連答権を表示し続けるのもおかしい（SD 開始時にクリアするのが自然）。
- 提案: `stepSd` で `markWin` を使う。あわせて `sdStart` で `holder = null` にする。

### R-05 🟡 1R 手動並べ替えの残り（scoreRound.ts `rank1R` / `setTieOrder`）
- `tieOrder` は選手ごとに保持され、点数を直しても消えない。A,D の同点ブロックで D を上にしたあと、D の点数を直して B,C と同点にすると、D が古い手動順 0 で B,C より上に来る（本来は受付番号順）。
- 1R 順位は全ラウンドの最後の決め手なので、静かに順位が変わるのは危ない。
- 提案: `setScore` で点数が変わった人の `tieOrder` を消す。または `setTieOrder` を「点数＋並び」の組として持ち、点数が違えば無視する。

### R-06 🟡 `wrongEndsQuestion=false` の同一問題での再解答
- `stepAnswer` は `questionWrongBy` を記録しているのに、F の休み以外では使っていない。2R なら ×→× で1問のうちに失格する。
- N1 の回答が「誤答後も他の人が押せる」だった場合に限って問題になる。「誤答した人はその問題では押せない」とするのが普通なので、G3 と一緒に仕様を決めてから `canAnswer` に入れる。

### R-07 🟡 途中での設定変更
- `config` は `RoundInit` の一部なので、ラウンドの途中で設定値（主催者の回答反映など）を変えて replay すると、**すでに進んだ部分も新しい設定で計算し直される**（例: `maxQuestions` を後から入れると、過去に遡って打ち切りになる）。
- 提案: ラウンドの開始時に設定値を固定して保存する（UI と保存の設計）。途中で変える必要が出たら「設定変更」イベントにする。control-dev に伝える。

### R-08 🟡 確定取消の条件
- `unfinalize` は「呼び出し側が確かめること」というコメントだけ。§1.2・§11 の「次ラウンドにイベントが無いときだけ」はエンジンの外に任されている。
- 提案: 大会全体の状態（ラウンドどうしのつながり）を持つ層に `canUnfinalize(roundId)` を作り、テストする。UI 側の作業になるので control-dev のタスクに入れる。

### R-09〜R-11 ⚪ 軽微
- R-09: N9 の暫定「途中棄権＝失格扱い」を早押しラウンドで入力する手段（`withdraw` イベント）が無い。N9 の回答が来るまで保留でよいが、当日の飛び入り・棄権は起こりうるので、手段は用意しておきたい。
- R-10: `replayTimer` は `start` を2回目以降無視するので、誤って開始するとやり直せない（トラブル用に、運営だけが使うリセットがほしい）。`pause.at < lastAt`（OS の時計補正）で経過時間が減る。UI 側で単調増加する時刻を使うよう注意する。
- R-11: `boundaryTies` はプレート境界 5/6・15/16・30/31 だけ。§5.2 は「同点ブロックがある場合、確定前に警告（特にプレート境界）」なので、同点ブロックの一覧も返すとよい（2R 以降の決め手になるため）。

### 仕様の確認事項（エンジンの不具合ではない）
- F で打ち切り → SD になったとき、休み中の人も SD に参加できる（`sdApply` は休みを見ない）。SD は別形式なので妥当と考えるが、rules_spec §10.5 に一言書いておくとよい。→ rules-architect
